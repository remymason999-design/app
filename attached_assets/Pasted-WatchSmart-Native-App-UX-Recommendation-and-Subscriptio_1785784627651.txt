4. Replace the current Watched action with useful feedback
Marking something as watched is not enough. We need to learn whether the user actually liked it.
When the user presses Watched, open a fast feedback sheet instead of immediately completing the action.
Feedback sheet
Title:
What did you think?
Primary options:
* Loved it
* Liked it
* It was okay
* Didn’t like it
Also include:
* Haven’t finished it
* Cancel
Data model
Store the watched interaction with fields similar to:

{
  user_id,
  title_id,
  interaction_type: "watched",
  watched_sentiment: "loved" | "liked" | "neutral" | "disliked",
  completed: true | false,
  created_at
}

Use the existing database naming conventions rather than blindly duplicating fields.

Recommendation weighting

Treat feedback approximately as:

Loved it      = very strong positive signal
Liked it      = positive signal
It was okay   = weak or neutral signal
Didn't like it = strong negative signal
Haven't finished it = incomplete signal, not a full dislike

The engine should learn from:

* genres
* subgenres
* cast
* directors
* writers
* themes
* tone
* audience type
* language
* release era
* provider
* community taste cluster

Do not treat every watched title as positive.

A disliked watched title must not strengthen recommendations for similar content.

UX requirements

* The feedback should take only one tap after pressing Watched.
* Confirm the response with a small animation or brief message.
* Then advance to the next card.
* Rewind must reverse both the watched action and its sentiment.
* Allow users to change this rating later from title details or viewing history.

5. Repair “For you both”

The current For you both results are clearly inaccurate. It is showing titles that do not reflect both users’ tastes.

Do not produce this list by simply joining two watchlists or using one person’s generic feed.

Correct logic

For every title, calculate:

joint_score =
  minimum(userA_score, userB_score)
  + mutual_genre_bonus
  + mutual_tone_bonus
  + shared_provider_bonus
  + community_quality_bonus
  - dislike_conflict_penalty
  - hard_skip_penalty
  - already_seen_penalty

Using the lower of the two individual scores is important. A title should not rank highly when one user is predicted to love it and the other is predicted to dislike it.

Exclude titles when

* either user has hard-skipped it
* either user has marked it watched and disliked it
* either user has hidden it
* neither user has access through their selected services
* it violates either user’s explicit content settings
* it falls outside important language or anime preferences
* the title is low quality or weak fallback inventory

Tabs

Keep these sections, but make their meaning accurate:

* Both — saved by both users
* You — saved only by the current user
* Friend — saved only by the friend
* For you both — newly recommended titles that should appeal to both

“For you both” must not contain existing watchlist items unless clearly placed in a separate shared-watchlist section.

Validation

Create automated test profiles such as:

* crime/thriller user + crime/drama user
* Marvel user + historical-drama user
* animation user + adult-thriller user
* almost identical users
* highly opposing users

Log for each result:

* both individual recommendation scores
* final joint score
* reason for recommendation
* shared genres
* conflicting preferences
* provider availability
* exclusion checks

The UI may show a short reason such as:

* “Matches both of your crime and mystery taste”
* “Popular with people who share both your tastes”
* “Available on a service you both use”

Never show a generic explanation unless it is supported by the score.

6. Add proper UK subscription plans

The app currently appears to store one price per service. That is not sufficient because most services have several plans.

Create a proper subscription plan structure.

Suggested structure

type StreamingPlan = {
  id: string;
  serviceId: string;
  name: string;
  monthlyPrice: number;
  annualPrice?: number;
  billingType: "monthly" | "annual" | "free" | "licence_required";
  hasAds: boolean;
  videoQuality?: string;
  simultaneousStreams?: number;
  minimumTermMonths?: number;
  active: boolean;
  region: "GB";
  sourceUrl?: string;
  priceVerifiedAt: string;
};

User subscription record

Each user must choose:

* service
* plan
* monthly or annual billing where available
* optional custom price
* whether it is included through another provider
* optional promotional end date

Example:

{
  service_id: "netflix",
  plan_id: "netflix-standard",
  billing_cycle: "monthly",
  effective_monthly_cost: 12.99,
  included_with_other_provider: false
}

Subscription selection UX

During onboarding and in Profile → Streaming services:

1. User selects the service.
2. A plan selector appears.
3. The user chooses their exact plan.
4. Show:
    * plan name
    * monthly price
    * ads or no ads
    * quality
    * streams where known
5. Allow Enter my own price because users may have:
    * legacy prices
    * bundles
    * promotions
    * student pricing
    * mobile-network offers

Do not silently guess the most expensive plan.

Savings calculations

All Savings figures must use the user’s selected plan, not a generic service price.

Annual cost should be calculated from the real billing choice:

monthly plan: monthly price × 12
annual plan: actual annual payment
free service: £0
bundled service: user-entered effective cost

The current monthly figure of £38.47 must therefore be recalculated after the user confirms their plans.
